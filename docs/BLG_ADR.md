# ADR-001 架構決策紀錄

## 1. 需求摘要（4 句話以內）
研究員設定股票池與參數並載入嚴格對齊可得時點的台股資料。系統計算多種因子特徵並產出對照組與智慧選股訊號，接著依據訊號組成投資組合執行嚴格扣除成本的月調倉回測，最後產出包含樣本外績效對比與圖表的評估報告。

## 2. 問題特徵
| 面向 | 本系統 |
|---|---|
| 系統類型 | 批次分析，非即時 |
| 資料特性 | 日、月、季頻資料 |
| 複雜度來源 | 多步驟處理 |
| 非功能需求 | 可重現、可稽核 |

## 3. 候選架構評估
| 架構 | 符合度 | 理由 |
|---|---|---|
| 管線 (Pipeline) | 高度符合 | 系統運作具備明顯的先後順序（資料->因子->選股->回測），各模組輸入與輸出明確，可單獨測試與抽換。 |
| 分層 (Layered) | 中等符合 | 介面邏輯可用，但本系統的核心行為偏向「資料流的轉換與清洗」，而非複雜的網頁業務邏輯與狀態疊加。 |
| 微服務 (Microservices) | 低度符合 | 屬於過度設計。專案為小組單機作業且無需即時連線，微服務的部署與維運成本遠高於實際收益。 |

## 4. 決策
選擇：管線架構（Pipeline Architecture）搭配規則式濾網

為何選它：每個步驟的職責邊界清晰，非常適合配合 BDD（行為驅動開發）針對單一環節進行自動化測試，且能最大程度保證歷史回測的「可重現性」。
為何不選其他：單機批次作業不需要微服務的高併發與分散式擴展能力，採用微服務會徒增除錯困難度與開發時間。
未來考量：若未來專案擴充，需要串接券商 API 進行盤中即時交易與監控，將會重新依據模組邊界，將報價接收與下單執行逐步拆分為事件驅動或微服務架構。

## 5. 目錄結構
```
app/
  data.py       載入、還原、對齊可得時點
  factors.py    因子計算
  portfolio.py  選股與權重
  backtest.py   成交假設與交易成本
  report.py     績效摘要
```
