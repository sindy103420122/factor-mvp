## 需求分析與 User Story 撰寫規範
當使用者要求 AI 協助「釐清、發想或修訂 User Story」時：

1. **嚴格符合標準格式**：
   - 必須遵守 `作為 [角色]，我想要 [功能]，以便於 [價值]` 三要素。
   - 必須附帶 3~5 項明確、可量化的 **「接受標準 (Acceptance Criteria)」**。
2. **範疇控制 (Scope Control)**：
   - 著重於「使用者要什麼 (What)」，**禁止在需求階段提前引入技術實作細節**（例如：不要在 User Story 寫出「使用 pandas」或「用 LightGBM」）。
   - 若需求過於模糊，請主動指出缺漏，並提供 2~3 個具體的延伸情境供使用者選擇。

---

## BDD Feature 轉譯規範
當使用者要求將 User Story 轉換為 BDD (`.feature`) 規格時：

1. **嚴格遵循 Gherkin 語法**：必須包含 `Feature`, `Scenario`, `Given`, `When`, `Then`。
2. **可測試性**：
   - `Given` 描述前置狀態，`When` 描述觸發動作，`Then` 描述可觀察的預期結果。
   - 每個 Scenario 只驗證一種行為；每個 Feature 至少 1 個成功情境與 1 個邊界／異常情境。
   - 使用具體日期與數字，避免「很多、很快、不錯」這類模糊用詞。

---

## 系統設計與程式碼生成規範
當使用者要求根據 User Story 或 BDD 規格「生成系統架構或程式碼」時：

1. **精準對齊，不做過度設計**：
   - 程式功能必須 100% 來自指定的 User Story / BDD 規格，嚴禁自行新增未要求的欄位或功能。
2. **MVP 原則**：採用最簡架構（管線：data → factors → portfolio → backtest → report），優先使用易於理解的技術棧（Python）。
3. **註解對應規格**：關鍵邏輯必須加上**繁體中文註解**，並標明對應的情境（例：`# 對應 Scenario: 公布前使用上一個月`）。
4. **主動提示不確定點**：規格與實作有衝突或疑義時，先標註「規格不確定點」並詢問，不要自行猜測。
5. **先問再做**：動手前，先列出你的假設與待確認問題。

---

## 因子投資專案專用規則
1. **Point-in-time**：任何因子只能使用「計算日（asof）當天以前已公布」的資料。不確定公布日時，標註「規格不確定點」。
2. **時間序列切分**：禁止隨機切分訓練與測試資料。
3. **成本**：回測一律扣除手續費與證交稅，並報告換手率。
4. **樣本外**：樣本外期間不得用於調整參數或選模型。
5. **MVP 範圍**：MVP 不做機器學習，只做規則式 baseline。

---

## 檔案與目錄產出規範
- 所有生成的系統程式碼**一律建立在 `app/` 目錄下**。
- 測試步驟（Step Definitions）放在 `features/steps/`。
- 嚴禁在專案根目錄生成任何 Python 程式碼檔案。
- 與 AI 的關鍵互動，請記錄到 `ai_log/`。
